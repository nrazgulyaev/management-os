# Smoke Test Route Matrix — Arconique Management OS

How the platform's routes are classified for smoke testing.  The
inventory is generated by `src/features/smoke-tests/route-inventory.ts`
(used both by the static script `scripts/smoke-routes.ts` and the
P114 test suite).  This document is the human-readable companion.

## Audience classes

| Audience | Origin | Auth model | Expected unauth GET |
|---|---|---|---|
| `public` | `src/app/(public)/**` | None | `200` (or `200_or_404` for parameterised hold-flow pages) |
| `auth` | `src/app/(auth)/**` | Pre-login flows (login, MFA setup, admin bootstrap) | `200` |
| `internal` | `src/app/(dashboard)/**` | Supabase auth + `app_users` + permission scopes | `302` (redirect to `/login`) |
| `owner` | `src/app/(owner)/**` | Owner-portal Supabase auth + access grants | `302` |
| `guest` | `src/app/(guest)/stay/[token]/**` | Stay token bound to the URL segment | `200_or_404` |
| `field` | `src/app/(field)/field/**` | Field-staff Supabase auth + role | `302` |
| `vendor` | `src/app/(vendor)/vendor/service/[token]/**` | Vendor token | `200_or_404` |
| `development` | `src/app/(development-app)/**` | Internal-only | `302` |
| `api-public` | `src/app/api/v1/holds/**`, `src/app/api/v1/quote/**` | Hold token (public booking flow) | `200_or_404` |
| `api-cron` | `src/app/api/cron/**` | `Authorization: Bearer <CRON_SECRET>` | `401` |
| `api-internal` | other `src/app/api/**` | Operator session | `401` |
| `api-token` | Token-scoped APIs (e.g. `/stay/[token]/requests/[code]/stream`) | Stay-token bearer | `200_or_404` |

## How smoke checks run

### Static (always — no live env required)

```bash
npm run smoke:routes
```

Walks `src/app/**`, classifies each `page.tsx` / `route.ts`, and asserts:

- ≥ 80 routes total inventoried,
- every required audience class has at least one route,
- every cron route expects `401` without a secret,
- internal pages are flagged as `302` (redirect-to-login).

This is wired into `npm run preflight:deploy` and runs in CI without
a live DB.

### Live (operator-driven)

After deploying staging:

1. Open `/dashboard/system/deployment` — env + production gates green.
2. Open `/dashboard/system/health` — module groups green.
3. Open `/dashboard/system/storage` — bucket privacy = private.
4. `curl -i` a few cron endpoints with no Authorization — expect
   `401`.
5. `curl -i` a public marketing page — expect `200`.
6. Walk the manual flows listed in
   `docs/STAGING-LAUNCH-CHECKLIST.md` § 7.

## When introducing a new route

1. Place the file under the correct route group so the audience is
   detected automatically.
2. If the route is parameterised, give it a sensible `[paramName]`
   directory.
3. Run `npm run smoke:routes` — output should still report `OK`.
4. If it's a new cron job, follow `VERCEL-CRON-CHECKLIST.md`.
5. If it's an internal admin surface that queries new tables, prefer
   `safeCount` / `safeList` from `@/features/system/db-health` so
   missing migrations don't crash the page.

## When a smoke check fails

| Failure | Likely cause | Fix |
|---|---|---|
| New audience class with 0 routes | Removed last route in that group | Re-add or update `REQUIRED_AUDIENCES` |
| Cron route expects `200` instead of `401` | Route is bypassing `handleCronJobRequest` | Wrap the route in the shared handler |
| Total routes < 80 | Massive deletion or wrong app dir | Investigate `git log -- src/app` |
| Internal route expects `200` | New layout that bypasses auth | Re-add the auth guard |
