# Write-flow correctness audit (2026-06-10)

Read-only static audit of critical write-flows. **Verdicts: 19 correct, 11 minor-issue, 16 bug, 1 cannot-tell. 29 defects (≈14 HIGH).**

## Dominant pattern: cross-tenant IDOR + missing audit-log on money-write server actions
Many actions load+write `WHERE eq(table.id)` with NO `organizationId` filter (any user acts on any org's row by id). Several money tables (distributions, distribution_allocations, payout_batches, payout_lines, contract_milestones, contract_groups) have **no organization_id column at all** → can't even scope. Server actions are independently callable, so a missing gate = exploitable.

## Bugs by severity

### HIGH
- **[capital-money]** Cross-tenant IDOR + unaudited money movement in the distribution waterfall. declareDistribution / executeDistribution / cancelDistribution / editDistribution (distribution-actions.ts) have NO org scoping, NO ownership check, and NO recordAuditEvent — and the distributions / distribution_allocations tables have no organization_id column at all (only nullable project_id). executeDistribution(id) is invoked from /development-os/distributions/[id]/page.tsx with the id taken directly from the URL behind only enforceProductAccess('dev') (org-has-product membership, not row ownership). Any user in any dev-enabled org can declare and execute a distribution against another org's project commitments, crediting real money (wallet_transactions + investor_wallets balances) into another tenant's investor wallets.
  - `src/lib/development/server/distribution-actions.ts`
- **[capital-money]** Distribution detail page exposes the money-moving executeDistribution / cancelDistribution server actions with no auth, org, or ownership check. The page never calls requireInternalUser / requireOrgId / getDistribution-with-org; getDistribution(id) and executeDistribution(id) both take the raw URL id. Combined with the table having no org column, this is the mounting point of the cross-tenant distribution IDOR.
  - `src/app/(development-app)/development-os/distributions/[id]/page.tsx`
- **[capital-money]** setStatementStatusAction is a cross-tenant IDOR with NO state-machine guard. It loads owner_statements BY ID with no organization_id filter (despite the table having organizationId and the sibling loadStatementForOrg pattern existing) and writes any status in {draft,issued,approved,paid,voided}. A finance-role user in org A can set org B's statement to 'paid'/'voided', and any status can transition to any other (e.g. draft->paid skipping approval, or paid->draft), so a statement can be marked paid that was never approved.
  - `src/features/finance/actions.ts`
- **[capital-money]** Payout flow has no tenant isolation: payout_batches and payout_lines tables carry no organization_id column. setPayoutLineStatusAction marks a line 'paid' (sets paidAt) by id with only a role gate and no ownership/org check, no state-machine guard (any->any in {pending,approved,paid,failed,cancelled}), and no double-pay/idempotency guard — a line can be marked paid without an approved batch or re-marked freely. createPayoutLineAction accepts ownerId/statementId from the form and its disputed-state check loads ownerStatements by id with no org filter, allowing a payout line to be attached to a cross-tenant owner/statement.
  - `src/features/finance/actions.ts`
- **[construction]** Cross-tenant money-write IDOR: markMilestonePaidByOperator selects + updates contract_milestones by eq(contractMilestones.id) with NO tenancy scoping. contract_milestones and contract_groups have NO organizationId column — tenancy is only transitive via projectId→projects.organizationId — and the action never joins to projects. Any authenticated internal user can mutate ANOTHER org's milestone paid amount/status by guessing the milestone UUID. The companion reads getInstallmentPlanDetail / listInstallmentPlans / getPlanDetailAction are also entirely un-org-scoped (list/return every org's plan).
  - `src/lib/development/server/installment-desk-actions.ts (markMilestonePaidByOperator, remindMilestone) + src/lib/development/server/installments.ts (getInstallmentPlanDetail, listInstallmentPlans)`
- **[construction]** Procurement flow has ZERO audit logging: procurement-actions.ts never calls recordAuditEvent on PR create/submit/approve, quotation add, winner selection, or PO creation — i.e. the money-moving + submittal-gated path leaves no audit trail. (Contrast: RFI=4, takeoff=5, coordination=11 recordAuditEvent calls.)
  - `src/lib/development/server/procurement/procurement-actions.ts`
- **[construction]** selectQuotation confused-deputy cross-org PO write: it SELECTs the quotation and PR by eq(id) with no organizationId filter, then INSERTs material_purchase_orders + material_po_lines using the SESSION org but with projectId/vendorId taken from the (possibly foreign-org) PR/quotation. PO FKs to projects/vendors are not org-constrained, so the insert succeeds — creating a real money PO in the attacker's org that references another org's project/vendor. The sibling-reject and PR-link UPDATEs are org-scoped (no-op cross-org), masking the partial success.
  - `src/lib/development/server/procurement/procurement-actions.ts (selectQuotation)`
- **[construction]** Unscoped IDOR reads in procurement: listPurchaseRequests and getPurchaseRequest call NEITHER requireInternalUser NOR requireOrgId and have no organizationId WHERE clause — they return any org's purchase requests and quotations to any caller. generatePurchaseRequestsFromBoqAction also fetches BOQ items by id IN(...) with no org filter and grafts foreign-org BOQ data into session-org PRs.
  - `src/lib/development/server/procurement/procurement-actions.ts (listPurchaseRequests, getPurchaseRequest, generatePurchaseRequestsFromBoqAction)`
- **[crm-portals]** markReservationPaid (buyer mark-paid) is an unauthenticated, unscoped, un-audited money-lifecycle state write. No requireInternalUser/requireOrgId/requirePermission, no recordAuditEvent, no status guard; WHERE is eq(reservations.id) on a client-supplied id. A server action is an independently-callable POST endpoint, so the layout's enforceProductAccess('dev') does NOT cover it - any authenticated org user can flip ANY org's reservation to status='active'/paidAt by id (cross-tenant IDOR), and can illegally re-activate a cancelled/expired/refunded reservation. extendReservationExpiry and cancelReservation in the same file share the identical no-auth/no-scope/no-audit defect.
  - `src/lib/development/server/reservation-actions.ts:229`
- **[crm-portals]** signContract (buyer e-sign) does an unconditional UPDATE contracts SET status='signed' WHERE id=<client id> with no auth gate, no org scope, no current-status guard, and no audit event. Allows (a) cross-tenant IDOR signing of any contract by id; (b) force-signing a draft/cancelled contract; (c) re-signing an already 'signed' contract, which re-fires the fully_signed cascade -> transitionLeadToBuyer (re-stamps the lead role to contract_signed/converted and re-writes unitDevelopmentMeta.contractPriceMinor / re-freezes the unit). The money value is correct bigint USD minor, but the unguarded re-entrant transition is the defect. convertReservationToContract in the same module has the same missing-auth/missing-audit pattern.
  - `src/lib/development/server/contract-actions.ts:313`
- **[crm-portals]** updateLeadStatus (the LeadStatusControl dropdown) is a second pipeline-status write path that completely bypasses the FSM and auth that moveLeadStage enforces. No requireInternalUser/requireOrgId/requirePermission, no leadTransitionError() guard, no audit_event; WHERE is eq(contactRoles.id) only. Permits cross-tenant IDOR status writes by id and arbitrary illegal transitions (e.g. new->contract_signed in one hop, or reopening a terminal lost/contract_signed) - it even stamps endedAt/endReason='converted'. Funnel integrity that moveLeadStage protects is defeatable via this sibling action.
  - `src/lib/development/server/lead-actions.ts:344`
- **[warehouse-direct]** Cross-tenant IDOR in createDirectBookingOnBehalfAction: villa lookup `select(...).from(villas).where(eq(villas.id, data.villaId)).limit(1)` (operator-create.ts:86-94) has NO organizationId scoping and no join to projects, contradicting its own comment that calls it 'the ownership guard'. villas carries no org column (tenancy = villas.projectId -> projects.organizationId) and quoteDynamicStay does not enforce org either. A caller with direct_booking.write can pass another org's villaId; insertHold stamps the hold with the CALLER's org while createInternalHoldBlockForDirectHold stamps the calendar block with the VILLA's (victim) org — creating an org-mismatched hold and an active calendar block on the victim org's villa. Fix: join projects and require projects.organizationId === requireOrgId() before pricing/holding.
  - `src/features/direct-booking/operator-create.ts`
- **[warehouse-direct]** Over-credit / unbounded re-receive in receivePurchaseOrder: quantity_delivered is clamped to ordered via Math.min (line 139), but the stock movement quantity (line 187: receivedQty.toFixed(4)) and the balance credit (line 213: `+ ${receivedQty}`) use the RAW receivedQty, not the clamped delivered delta (newDelivered - alreadyDelivered). Combined with the absence of any fully_delivered / idempotency guard (only status==='cancelled' is blocked, line 89), an already-fully-delivered PO line can be received again repeatedly: quantity_delivered stays clamped (no visible change) while quantity_on_hand is credited the full receivedQty each time and a new 'received' movement is written — inflating stock without bound and diverging on-hand from delivered. Fix: credit/move the clamped delta (newDelivered - alreadyDelivered) and reject receiving against fully_delivered lines.
  - `src/lib/development/server/warehouse/warehouse-receipt-actions.ts`
- **[leakage]** Cross-tenant leak in executive snapshot reads: getLatestCompanySnapshot(), getLatestProjectSnapshot(projectId), and listRecentCompanySnapshots() filter on scope/projectId only and ignore the executive_metrics_snapshots.organization_id column (which the write path stamps). The /development-os/dashboard page calls getLatestCompanySnapshot() with no requireOrgId() gate, so in a multi-org deployment any dev-os user reads whichever org's newest company-wide financial snapshot (cash, receivables, payables, blended margin, pipeline value, committed/drawn investor capital). getLatestProjectSnapshot(projectId) additionally accepts an arbitrary projectId with no org/ownership check (IDOR). Fix: thread requireOrgId() into the page and add eq(executiveMetricsSnapshots.organizationId, orgId) to all three queries. Masked today only because persist falls back to ARCONIQUE_DEFAULT (single-tenant).
  - `src/lib/development/server/executive/metrics-queries.ts`

  - `src/lib/development/server/rfis/rfi-actions.ts (respondToRfi, transitionRfi)`
- **[construction]** Coordination IDOR: transitionCoordinationItem (RFI + submittal branches), removeCoordinationPin, projectIdForRevision and the placeCoordinationPin belongs-checks all query by eq(id) with no organizationId filter (submittals/rfis/coordination tables all carry an org column). - **[crm-portals]** Owner payout 2FA confirm-step has no brute-force protection: updatePayoutMethodAction does NOT invalidate the challenge cookie or count attempts on a wrong code, so the 6-digit code (1,000,000 space) can be guessed with unlimited tries inside the 10-minute window. The gate IS owner-bound and server-re-verified (so it is not a trivial bypass), but once real SMS/email transport replaces the in-response demoCode, a session-hijack attacker who lacks the out-of-band code could brute-force it. Burn-after-N-failures or a rate limit is needed. Also the hash salt (HASH_SALT) is a hardcoded public constant rather than a server secret.
  - `src/features/owner-portal/payout-edit-actions.ts:155`
- **[warehouse-direct]** dispatchPick to a project or villa destination always fails: it sets toLocationId = (kind==='location' ? destId : null) with movementType 'issued_to_site', but applyMovementToBalance('issued_to_site') requires BOTH fromLocationId and toLocationId and throws 'issued_to_site: both from and to location required'. listPickDestinations offers project:/villa:/location: options, so the two most common pick destinations error out before any write; only location: picks succeed. Fix: model issue-to-project/villa as a debit-only movement (or route through a consumed/site location), passing fromLocationId only.
  - `src/lib/development/server/warehouse/warehouse-flow-actions.ts`
- **[warehouse-direct]** Movement-code generation race across all three inventory write paths: movement_code 'INV-YYYY-####' is derived from `COUNT(*)+1` over dev_os_inventory_movements (warehouse-receipt-actions.ts:120-124, warehouse-stock-actions.ts:123-127, inventory-actions.ts:121-126). movement_code carries a UNIQUE constraint, so two concurrent transactions (or a collision with pre-seeded codes) will both compute the same next sequence and one will fail the unique insert, aborting an otherwise valid receive/count/pick. No data corruption, but spurious failures under concurrency. Fix: use a DB sequence / advisory lock / ON CONFLICT retry.
  - `src/lib/development/server/inventory/inventory-actions.ts`
