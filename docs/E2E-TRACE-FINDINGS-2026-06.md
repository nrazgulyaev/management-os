# E2E static-trace findings — remaining (2026-06)

From the 8-flow static trace. The 6 HIGH items were fixed in the same PR. These MED/LOW remain — some are quick fixes, a few need a product/money decision (flagged).

## MED
- **[New-tenant ONBOARDING + provisioning → first ]** signupAction grants only super_admin in user_roles via assign_user_role and never creates an app_user_roles (cabinet) row, whereas route.ts grants both via provision_app_user('super_admin','admin'). It also sets organizations.trialStatus='active' + trialStartedAt/EndsAt on the org row, while route.ts leaves trialStatus='none' on the org and instead writes trial dates to org_subscriptions. First dashboard render survives both (super_admin bypasses product+cabinet gating; trial banner derives cleanly), but the two provisioning paths produce structurally different tenants — a latent source of role/cabinet-routing and trial-banner inconsistencies for cabinet-scoped (non-super-admin) features. Should be unified, but doing so safely needs a product decision on the canonical shape.
- **[New-tenant ONBOARDING + provisioning → first ]** Same class as the fixed route.ts bug but in the server-action path: insert organizations → insert appUsers → assign_user_role → sendEmail run sequentially with no DB transaction and no auth-user rollback in any catch. A failure after the org insert (e.g. assign_user_role RAISE, or sendEmail/resendProvider throwing when RESEND is configured) leaves an orphaned org + possibly orphaned app_user AND an orphaned auth user. I did not wrap it because the surrounding redirect()/revalidatePath() control flow (redirect throws NEXT_REDIRECT and must stay out of try/catch) makes a safe transaction wrap a larger refactor than a pure guard-clause fix.
- **[New-tenant ONBOARDING + provisioning → first ]** When ctx.appUser?.organizationId is falsy, requireOrgId() falls back to the ARCONIQUE_DEFAULT seed org id. A freshly-provisioned-and-logged-in tenant always has organizationId (NOT NULL), so this does not mis-scope their dashboard; but it remains a documented cross-tenant data-leak hazard for any anonymous/unauth render path that reaches an org-scoped query. Pre-existing design decision (COMPLETE-1) outside this flow's deterministic crash class — flagged, not changed (removing it would 500 the unauth smoke/probe paths it was added to protect).
- **[BOOKING lifecycle: create booking → guest sta]** setBookingStatusAction accepts any valid status enum value with no state-machine guard — visibility is only enforced client-side (CheckOutButton renders only when status==='checked_in'). A direct call could move a booking to checked_out from cancelled/no_show/inquiry, unlike the strict checkins state-machine used for the online flow. Not a crash, but an integrity gap; needs a business-rule decision before adding a server-side transition guard.
- **[BOOKING lifecycle: create booking → guest sta]** listAvailableVillaTypes() queries villas with no organization/project org filter (every other query in this flow is org-scoped via requireOrgId). On a multi-tenant DB this can surface other orgs' villas/types as bookable. Tangential to crash-tracing and likely tracked under the broader tenancy sweep, but flagged here — needs verification that the calling form path is otherwise scoped.
- **[Finance owner statement: generate → review/ap]** There are TWO generators with different net-to-owner formulas, FX handling, and sign conventions writing the same owner_statements table. statement-generation.ts computes net = gross − channelFee − expense − tax − reserve − operatorFee with tax=11% and reserve=3% hardcoded and FX snapshotted; statement-generator.ts sums gross + fees + expenses + taxes + reserves + mgmtFee relying on source rows already being stored signed, and never sets period_month or net_to_owner_usd_minor. Whether the two produce reconcilable 'net to owner' numbers for the same owner/villa/month, and whether the manual generator's source-row sign convention is correct, needs runtime verification with real seeded fee/expense/tax rows. Not changed per instruction (prior sweep money-verified the manual generator's net via read-only replay).
- **[PAYOUT: create payout line/batch → advance pe]** A batch has a single currency, but a payout line's currency is chosen independently in PayoutLineForm (USD/IDR/EUR/GBP/AUD/SGD) and createPayoutLineAction never validates that a line's currency matches its batch. listPayoutBatches sums all lines' amountMinor across mixed currencies into one bigint and renders it under the batch currency — e.g. 1,000,000 IDR minor + 100 USD minor displayed as one USD figure. This is a real money-miscompute on a mixed-currency edge case, but the correct behavior (reject mismatched currency at line creation vs. group/convert) is a business decision I cannot verify, so no math was changed.
- **[PAYOUT: create payout line/batch → advance pe]** There is NO action or UI to ever advance a payout batch out of 'draft' (no setPayoutBatchStatus action exists). The approvedBy/approvedAt/paidAt columns on payout_batches are never written, and the page's 'approved'/'paid' batch badges are unreachable. The pending→approved→paid lifecycle only works at the LINE level; the BATCH money lifecycle is backend-built-but-no-button. Not a crash, but the batch half of the flow is non-functional.
- **[Owner Portal — owner logs in → home / stateme]** getOwnerStatementById scopes by requireOrgId() (the CURRENT user's org). For a super-admin impersonating an owner whose villas live in a different org than the super-admin's own appUser.organizationId, the org filter could fail to match and the page would notFound() even for a legitimately-impersonated owner's statement. Needs runtime testing with a real cross-org impersonation session to confirm whether the super-admin's org resolves to the impersonated owner's org; the owner-context resolver hops owner→villa→project→org but getOwnerStatementById does not use that path.
- **[GUEST STAY + DIRECT BOOKING (public/token pat]** Unlike every sibling token sub-page (page.tsx, check-in, requests, requests/[code]), the Services page does NOT run rateLimitStayTokenAccess or the canAccessStayWithoutVerification gate before calling getGuestStaySummaryByToken — it skips verification entirely. A holder of an unverified token can browse the services catalog and reach GuestServiceRequestForm. Not a crash, but a verification-gate bypass inconsistent with the rest of the portal. Left for review since adding the gate changes access behavior (needs product confirmation it should be gated).
- **[GUEST STAY + DIRECT BOOKING (public/token pat]** When a guest_stay_token was issued with NEITHER issuedToEmail NOR issuedToPhone, channel='manual' and recipient=null. In production (devCodePreview suppressed) the guest can never receive a code — a hard dead-end. The VerificationForm renders a graceful 'contact your host' message (no crash), but there is no path to actually verify. This is token-provisioning/product policy, not a mechanical bug; needs a runtime/product decision (e.g. block issuing such tokens, or surface a concierge-issue flow).
- **[GUEST STAY + DIRECT BOOKING (public/token pat]** insertHold() and insertRequest() never set organization_id even though the villa→project chain (and require... ) could resolve it; the hold/request rows are created with NULL org on the public path. Downstream notifications/conversions then fall back to `?? null`/`?? undefined`. This matches the documented nullable-org TENANCY debt (migration 0153/0176, backfilled) and does not crash, but means guest-status message threads (getOrCreateGuestMessageThreadForToken also omits org) and direct-booking holds created via the public API won't appear in org-scoped admin lists (listAdminThreads filters on organization_id). Needs the org-resolution-on-create work, not a blind guard.
- **[OPERATIONS — turnover board, maintenance, ser]** The schema/action permit creating a maintenance ticket with BOTH villaId and projectId null (unlike createPreventiveScheduleSchema which has a .refine requiring villa-or-project). Such an orphan ticket has no row-level org linkage at all, so even after the detail-reader fix it cannot be safely org-scoped and will read as not-found on its detail page. Recommend adding a .refine((d)=>d.villaId||d.projectId) to createMaintenanceTicketSchema — left out here because it changes form validation (feature-ish) rather than being a pure null-guard.

## LOW
- **[New-tenant ONBOARDING + provisioning → first ]** route.ts has NO pre-check for an existing app_users/email row (unlike signupAction which selects appUsers.email first); it relies solely on admin.auth.admin.createUser returning an 'already registered' error. If auth.users and app_users ever diverge (orphaned app_users row from a deleted auth user, or vice versa), the two paths behave inconsistently and could create a duplicate app_users row or a confusing 500. Needs runtime state to reproduce; not a deterministic crash.
- **[New-tenant ONBOARDING + provisioning → first ]** route.ts builds /login?onboarded=1&email=<addr> but the login page (and form) only read ?onboarded; the email is never prefilled. Cosmetic UX gap, no crash.
- **[New-tenant ONBOARDING + provisioning → first ]** The page awaits all 12 mapPoolAll queries BEFORE evaluating the isEmptySystem() zero-state, so even a brand-new empty org runs every cabinet rollup query on first render. All queries are .catch-guarded and org-scoped (degrade to empty), so it won't hang PROVIDED a DB statement_timeout is set; per MEMORY (DB-STATEMENT-TIMEOUT-1) the statement_timeout decision is still operator-pending. If no timeout is configured, a degraded/slow unscoped query could still stall toward the function timeout. Needs runtime/infra verification.
- **[SETUP: create project → villa → team/roles (G]** const source = allVillas[0]?.source ?? 'mock' (villas page line 56) and projects[0]?.source ?? 'mock' (projects page line 22): for a real but empty tenant the array is empty, so the SourceBadge defaults to 'mock', falsely labelling a live empty workspace as mock/demo data. Cosmetic (misleading badge), not a crash; needs a product decision on the right default for empty-live, so not auto-fixed.
- **[SETUP: create project → villa → team/roles (G]** The Members <tbody> has no length===0 empty-state row (unlike the pending-invitations table which does). In practice the current admin always appears so it never renders truly empty, but if userRows were ever empty the table would show only a header with no guidance. Defensive gap, not a live crash.
- **[SETUP: create project → villa → team/roles (G]** saveOnboardingProgressAction is fired inside startTransition without awaiting/surfacing its result, so a failed persist (e.g. transient DB error) is silently swallowed — the user can navigate steps but progress may not actually save, with no feedback. No crash; needs runtime testing to judge impact.
- **[BOOKING lifecycle: create booking → guest sta]** extendBookingStayAction's overlap conflict query does not exclude cancelled/no_show on the boundary the same way create does — it uses sql NOT IN ('cancelled','no_show') which is correct, but it does not re-validate against active villa calendar blocks / holds (create uses assertHoldDatesStillAvailable). An extension could overlap an internal hold. Needs runtime confirmation of intended behaviour; not a deterministic crash.
- **[BOOKING lifecycle: create booking → guest sta]** settlementPanel derives statusTone from payment?.status / b.statement?.status with a final fallback to 'success' even when there is no payment and no statement in a non-draft state; combined with the (payment || b.statement) badge guard this is cosmetic only, but the 'success' default could mislabel an unpaid booking as settled in some branch combinations. Needs visual/runtime check; no crash.
- **[Finance owner statement: generate → review/ap]** generateAllForPeriod -> generateAllPendingStatements returns [] for a month with no qualifying bookings (fresh tenant, or wrong month). The page's generateForPeriodAction then redirects with no toast/notice, so the operator gets zero feedback distinguishing 'generated 0' from success. Cosmetic UX gap, no crash.
- **[Finance owner statement: generate → review/ap]** markStatementSent transitions status to 'sent' and arms the owner lifecycle even when the email send fails (emailReason is returned but the state still advances). This is intentional per the inline comment (operator can resend), but it means an owner can be marked 'pending/awaiting' with the 14-day auto-ack timer started while never actually receiving the email. Needs product confirmation, not a code fix.
- **[PAYOUT: create payout line/batch → advance pe]** Unlike createPayoutBatchAction (wrapped in try/catch), the line insert is unguarded. If the insert ever returns an empty array (FK violation surfacing differently, RLS, or a future trigger), row.id throws an unhandled TypeError that surfaces as a generic 500 to the user instead of a friendly action error. Not deterministically reachable on a normal insert, so left as-is rather than speculatively wrapping.
- **[PAYOUT: create payout line/batch → advance pe]** paidAt is stamped when next==='paid' but never cleared on any other transition. PAYOUT_LINE_TRANSITIONS makes 'paid' terminal (paid:[]), so today a paid line can't move back and this is consistent. Flagged only as a latent coupling: if the transition table is ever relaxed to allow paid→approved/failed, a stale paidAt would persist. No fix needed under current rules.
- **[PAYOUT: create payout line/batch → advance pe]** The status action accepts next:'pending', and the client TRANSITIONS map labels a 'Reopen' (→pending), but no state in PAYOUT_LINE_TRANSITIONS lists 'pending' as a valid target, so the server always rejects it with a transition error. Dead/misleading affordance rather than a crash; needs a product call on whether reopen-to-pending should exist.
- **[Owner Portal — owner logs in → home / stateme]** getMyStatementDetail's SQL filters owner-visible statuses but does NOT guard `period_month IS NOT NULL` (unlike listMyStatements, which does). It then runs `sr.period_month.split('-')`, which would throw on a NULL period_month. Currently latent: no page wires this export (the statement detail page uses finance/services getOwnerStatementById instead), and getTwelveMonthNetSeries is likewise unused. Left unfixed to avoid touching unverifiable dead code; would become a live crash if a page ever adopts it for an issued/approved/paid statement that has a NULL period_month.
- **[Owner Portal — owner logs in → home / stateme]** OwnerStatusPill renders LABEL[state] with no fallback; statements list casts `s.ownerState ?? 'pending'` to OwnerStatementState. DB owner_state currently matches the 6-state enum so this is safe today, but a legacy/unknown owner_state value (e.g. from an older migration) would render a blank pill label rather than a fallback. Cosmetic only; needs DB-value audit to confirm no stray states exist in production.
- **[Owner Portal — owner logs in → home / stateme]** The home upcoming-bookings read and listOwnerThreads filter by owner-owned villaIds / owner_id only, not by organization_id. This is tenant-safe in practice (an owner only owns villas/threads in one org), but it is defense-by-data rather than an explicit org predicate — unlike get-inbox.ts getOwnerInbox which does AND the org. A genuine cross-tenant leak would require a corrupted ownership_shares/owner_threads row; flagging for a tenancy reviewer rather than fixing blindly.
- **[GUEST STAY + DIRECT BOOKING (public/token pat]** For a token that does not exist at all (fresh tenant / typo'd link), canAccessStayWithoutVerification returns allowed=false, so StayHome redirects to /stay/[token]/verify, where getStayByToken returns reason='invalid' and the page calls notFound() (bare 404). The friendlier StayUnavailable 'Stay link not recognised' copy in StayHome is therefore unreachable for nonexistent tokens (it is still reachable for previously-verified-but-now-expired/revoked tokens). UX inconsistency only; reorder would change the verification gating so left as-is.
- **[GUEST STAY + DIRECT BOOKING (public/token pat]** If a guest submitted but deposit creation failed (ensureDepositForRequest returns null on a provider-session error), handleGetDepositForHold returns 404 ('deposit_not_found') and the payment page calls notFound(). The happy path redirects to /submitted (static) so this is only reachable by manual navigation to /payment, and the /status page degrades gracefully — but a direct hit on /payment is a 404 dead-end rather than a 'contact concierge' message. Needs runtime confirmation of the failure frequency before adding an empty-state.
- **[OPERATIONS — turnover board, maintenance, ser]** const [row] = await db.insert(...).returning({id}); then preloadCountLinesForLocation(row.id, ...) and row.id are used with no guard. If the insert returns an empty array (e.g. an ON-CONFLICT/RLS edge), row is undefined and row.id throws. Defensive only; a returning() insert normally yields the row, so low priority and not clearly reachable.
- **[OPERATIONS — turnover board, maintenance, ser]** readTurnoverRows joins bookings only via turnovers.sourceBookingId and hardcodes checkOut '11:00' / checkIn null (TODO acknowledged in code). Not a crash, but the board never shows real checkout/checkin times and the bookings join column (createdAt as checkOut) is unused/misleading. Needs product decision + real checkout_time/checkin_time columns; runtime behavior is correct (no crash), just incomplete data.
